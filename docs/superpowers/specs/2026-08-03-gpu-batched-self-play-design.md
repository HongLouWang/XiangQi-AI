# GPU 多局同步批量自我对弈设计

## 目标

在单个 CUDA 进程中同步推进多盘中国象棋自我对弈，将多盘 MCTS 的叶子节点合并为神经网络 batch，以提高 A100 等大显存 GPU 的利用率和训练吞吐量。验收不设固定加速倍数，以相同模型和搜索参数下的局/小时、GPU 利用率和峰值显存作为基准指标。

## 范围

- CUDA 模式新增多局同步批量 MCTS。
- 默认请求 16 个并行棋局槽位。
- CUDA OOM 时自动按 `16 → 8 → 4 → 1` 降级。
- 保留 CPU 多进程自我对弈路径及其配置语义。
- 保持合法走子、将死立即结束、最多 512 个完整回合（1024 ply）及上限和棋规则不变。
- 保持 Replay、双槽 checkpoint、暂停、追加和断点续传能力。

不采用多个 CUDA 进程，也不在本阶段实现单盘棋内部的虚拟损失并行。

## 架构

### CUDA 批量自我对弈调度器

CUDA 训练器只加载一份模型并维护一组独立棋局槽位。每个槽位拥有：

- 当前棋盘状态；
- 当前回合的独立 MCTS 树；
- 已走 ply 数和训练样本历史；
- 独立、可恢复的随机种子状态；
- 完成、失败或等待补位状态。

调度器每轮从每个活跃槽位选择一个待评估叶子，将所有叶子编码后堆叠为单个 Tensor batch。网络执行一次前向推理，再按槽位拆分策略与价值，完成各自节点扩展和回传。某个槽位达到本回合搜索次数后，从该槽位根节点选择合法走子并进入下一回合。

所有槽位的树、访问计数、历史和随机状态相互隔离；共享的只有网络前向调用。

### 槽位补充与停止

当一盘棋自然终局或达到 1024 ply 上限时，调度器生成最终价值标签并把完整棋局原子提交到 Replay。若目标局数尚未满足且没有暂停请求，则立即向空槽位补入一盘新棋，使 GPU batch 尽量保持饱满。

达到目标局数或收到暂停请求后，不再创建新棋局。已有活跃棋局继续到安全终局，提交 Replay 后保存 checkpoint，分别进入 `completed` 或 `paused`。

## 配置

新增配置字段：

- `parallel_games`: 请求的 CUDA 并行棋局数，默认 `16`，必须为正整数。
- CLI 参数 `--parallel-games`，用于 `train`；`resume` 可覆盖 checkpoint 中的值。

CPU 模式忽略 `parallel_games`，继续使用 `self_play_workers`。CUDA 模式的 `self_play_workers_effective` 保持为 `1`，另行报告有效并行棋局数，避免把进程数和棋局并行度混淆。

Colab Notebook 默认设置 `PARALLEL_GAMES = 16` 并传入 `--parallel-games 16`。

## OOM 自动降级

CUDA 并行度候选值从请求值构造，默认请求 16 时为 `16、8、4、1`。若请求值不是 2 的幂，则每次取不大于当前值一半的正整数，最终包含 1。

仅捕获明确的 CUDA out-of-memory 错误。其他 CUDA 或程序错误继续按现有失败协议记录，不得伪装为可降级 OOM。

OOM 发生后：

1. 不重复提交已写入 Replay 的棋局。
2. 丢弃尚未提交的活跃棋局内存状态。
3. 释放相关 Tensor，调用 CUDA cache 清理。
4. 将有效并行度降至下一候选值。
5. 从最近有效 checkpoint 和 Replay manifest 恢复，再继续训练。
6. 若并行度 1 仍 OOM，则写入 `failed` 状态并退出。

checkpoint 必须在开始一批可能 OOM 的活跃棋局之前已经覆盖所有已提交 Replay，确保重启边界明确。

## Checkpoint 与兼容性

checkpoint 配置保存 `parallel_games`。旧 checkpoint 缺少该字段时按默认值 16 加载，不改变网络结构或模型权重格式。

不把尚未完成的棋局或 MCTS 树写入 checkpoint。本阶段仍采用“只在完整棋局边界持久化”的协议，以避免复杂、巨大的树状态序列化。Runtime 被终止时，最多丢失当前尚未提交的活跃棋局；已提交 Replay 和最近 checkpoint 保持一致。

Replay 条目格式不变，因此 CPU 与旧版本生成的数据仍然兼容。

## 状态与可观察性

训练状态的 `message` 或等价稳定字段应报告：

- `self_play_workers_effective=1`；
- `parallel_games_requested`；
- `parallel_games_effective`；
- 最近一次网络推理 batch 大小；
- OOM 降级次数；
- 可计算时的累计局/小时。

日志记录每次并行度选择、OOM 原因、降级、恢复位置和有效 batch 大小，不记录棋局完整敏感载荷。

## 合法性与确定性

- 每次走子仍由现有规则引擎的合法走法集合产生。
- 将死、困毙或现有规则定义的自然终局立即结束。
- 未提前终局时最多 1024 ply，并按现有规则标记和棋。
- 每个槽位从全局 seed 和棋局编号派生独立 seed；调度顺序变化不得导致槽位之间共享随机状态。
- 相同 seed、模型、配置和有效并行度应产生可复现的调度与样本顺序；发生 OOM 降级后只要求从恢复点开始按新并行度可复现。

## 测试

### 单元测试

- 多状态 batch 推理与逐状态推理结果在数值容差内一致。
- batch 的策略、价值正确映射回原槽位。
- 各槽位 MCTS 树、访问次数、历史和随机状态互不串线。
- 单槽位模式与现有自我对弈输出结构兼容。
- 非法走子永不进入历史，终局和 1024 ply 上限保持正确。
- 并行度候选序列和 OOM 降级顺序正确。
- 非 OOM 异常不触发降级。
- OOM 恢复不重复写入 Replay。
- 暂停停止补位，但等待活跃棋局安全提交。
- CPU 多进程测试保持通过。
- 新旧 checkpoint 配置均可加载。

### 集成测试

- 使用小网络、低 simulations 和多个并行棋局完成端到端训练、暂停、追加与恢复。
- 无 CUDA 环境通过可注入的假批量网络和模拟 OOM 验证调度逻辑。
- CUDA 环境执行真实 batch smoke，确认模型和 Tensor 位于指定 GPU。

### Colab 基准

在同一 A100 Runtime、相同模型、`simulations=64`、相同局数和相同随机种子下，对比单槽位与自动 16 槽位：

- 完成局数/小时；
- GPU 平均利用率；
- 峰值显存；
- 平均实际 batch 大小；
- 是否发生 OOM 降级；
- 非法走子、checkpoint 或 Replay 错误数必须为零。

不要求预先承诺固定倍数。若吞吐未明显改善，应根据实际 batch 大小、CPU 走法生成时间和 GPU 利用率定位下一瓶颈，而不是盲目增加 CUDA 进程。
